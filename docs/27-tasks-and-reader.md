# Tasks, the quarantined reader and permission prompts

> **Status:** tasks and the reader in the agent VM since v0.7.0, permission prompts since v0.8.0, model fallback since v0.8.5. Code: `harness/` (task ids, lifecycle, held requests, taint), `guard/tasks.go` (`Host`: start, follow, cancel, resume), `app/tasks.go` (the `/tasks` API), `queue/` (the versioned SQLite queue), `guard/reader.go` (the reader), `guard/permission.go` and `guard/prompts.go` (permission prompts), `guard/fallback.go` (model fallback).

Builds on [harness/v1](20-harness-protocol.md), [gateway v0 and the vault](21-gateway-v0.md), [safety controls](23-safety-controls.md) (the reader's model call is budgeted and checked like any other) and [activity records](24-activity-records.md) (the reader's numbers and the taint are on the record).

## 1. Tasks
- **Ids.** `tk_` plus 26 lowercase base32 characters (128 bits). A start with a once-only key gets an id derived from the user and the key (HMAC under a key from dstack's KMS), so a retried start finds the same task instead of making a second one.
- **Lifecycle.** `queued`, `running`, `waiting/<why>`, `paused/<why>`, then `done`, `failed` or `cancelled`. The runtime owns the state. A request the guard holds for a person's decision is journaled `held` and stays held across a restart (never "interrupted"). The three-attempt cap counts brain failures only, not restarts.
- **API.** `POST /tasks` (start), `/tasks/status`, `/tasks/events` (server-sent events from any sequence number, so a closed tab reconnects and sees every event once), `/tasks/cancel`. EHBP-encrypted bodies like `POST /run`; the task id is inside the encrypted body; only the starter's tag sees a task. `POST /run` is a shim over the same task model.
- **Restarts.** Open tasks are resumed after an agentd restart, with their budget and activity record taken up. Ended tasks are pruned after a day.
- **Billing witness (v0.8.5).** The relay charges a run when it starts and may give the charge back only on the VM's word, in plaintext response headers (the bodies stay encrypted): a start says `X-Agent-Task: new` or `existing` (a repeated once-only key found the running task, so nothing new runs) and `X-Agent-Bill`, an opaque bill id (an HMAC of the task id under a key from dstack's KMS); a cancel says the same bill id and `X-Agent-Refundable: 1` only on the task's first cancel before any model output (reasoning, text or a tool call). Whether output happened is rebuilt from the stored events after an agentd restart. A cancel isn't persisted, so an agentd crash inside a cancel's grace period could make a second cancel refundable (one extra refund at most).
- **Open tasks (v0.8.5).** `GET /tasks/open` (bearer token) answers `{"open": n}`, a count only, so the relay's idle timer doesn't stop a VM that still runs a task nobody's tab follows.
- **`/run`.** Kept for one more release for tabs loaded before the chat moved to tasks, and for temporary chats until an ephemeral task exists (cancelled when its last follower leaves, deleted at its end); then removed.

### Model fallback (v0.8.5)
A slow or overloaded model used to end the run.
- **Request:** `fallback_models` (in the caller's order) and `auto_fallback` (true on Auto, false for a hand-picked model). The VM keeps only fallbacks the signed policy layers and its model list allow, in order, at most 5, never the run's own model, and drops the rest without refusing the run. A hand-picked run keeps none.
- **Detection, per model call:** no first token (reasoning, text or a tool call) within `min(120 s, 20 s + ceil(max(0, bytes - 64 KiB) / 32 KiB) s)` of the request body's size, or a 503, a 429 or an "overloaded" error (also one in the stream before any token). Then the event `{type:"model_slow", step, model, waited_ms, fallback}`.
- **Auto:** the call is cancelled and the step runs again once, on the first allowed fallback, then `{type:"model_switched", step, from, to}`; the run's later steps go straight to that model. One switch per run. **Hand-picked:** a slow model is waited for; an overloaded one ends the run with code `model_overloaded` and fixed words, never the provider's text.
- **Record and metrics:** the start record lists every model the run may call; a given-up call is a model call with outcome `abandoned_slow` or `overloaded`, its time and no tokens, followed by the call that answered, named by its model. Each model metric names its model; a given-up call's outcome is `slow_switched`.
- **Billing unchanged:** the run is charged at its own model's price, whatever model answered.
- **Test hook:** `gatewayd -e2e-model-fault <model>=slow|overloaded` is for the end-to-end overlay only; the verifier's release rule refuses a compose that sets it.

## 2. The queue
One SQLite file per space on the VM's encrypted disk, the runtime its only writer: tasks (start, options, attempts, state, taint), steering, the journal (every model call, action and exec, recorded before it runs), checkpoints and events. The schema is versioned (`PRAGMA user_version`) and only migrated forward, one transaction per step: 1 is the first release's tables, 2 the task model, 3 the taint. A file newer than the code is refused.

**Rolling back to v0.6.0.** v0.6.0 predates the version number: it doesn't read it and uses only version 1's columns, which a migrated file keeps (the newer columns have defaults), so it runs on the file as is. Tasks open at that moment are cancelled at its boot, as after any restart. Back on v0.7.0, `Open` gives the tasks v0.6.0 ended their state and end time and drops events of tasks it deleted (`TestOlderReleaseOnMigratedFile`).

## 3. Agent definitions, sponsors, triggers (later)
Signed agent definitions, the person an unattended agent runs on behalf of, schedules and steering rights. Not in the VM yet.

## 4. Approve before send (later)
Any send or share, and any change from a tainted task, will be held until a person approves that exact effect with a passkey. `harness.HoldGuard` and the `held` journal state are the runtime's part, in the VM since v0.7.0; the approvals themselves aren't.

## 5. The quarantined reader
A model call with **no tools**, made by gatewayd, never by the brain. It turns one untrusted item (a fetched page, or one search's titles and snippets as a batch) into fixed fields. The acting model gets those fields and quote references, never the source's text. Same pattern as the "dual LLM" and CaMeL: the model that can act never reads the untrusted text, and the one that reads it can't act.

- **Model:** gpt-oss-120b at low effort, through the model gateway: the verified upstream, a leased key, the policy's models, counted in the budget (agentd reserves the reader's largest call with the action) and on the activity record.
- **Fields:** summary, facts, entities, dates, amounts, source (kind, a short title in the reader's words, publisher, date), quotes (id, location, topic, and since v0.8.4 the first and last span, not the text), wording (for exact-wording questions), and an instruction count.
- **Checked by plain code:** the answer must decode strictly into the schema (exact members, types, enum, caps) or it is refused whole, never repaired; a tool call or a cut-off answer is refused; each quote must be found in the source and is shown as the source has it; 40-character passages of the source copied into the reader's own fields are cut (20 characters when the reader counted an instruction), and so are instruction-like sentences; links it writes are removed; credentials are redacted before it reads.
- **What the acting model sees:** the fields, the source's number and site (scheme and host; since v0.8.2 never the full address, where a page author's text could ride in paths, queries and redirect targets), and each quote as `[quote N]` with its location, topic and length. Never page text, snippets, a page's or result's own title, or quote text. Image search gives it only each image's site, not the titles. The person's stream carries the exact quotes (`tool_result.quotes`), so the browser shows the words where the answer cites `[quote N]`.
- **Sources by number** (since v0.8.2). The acting model fetches a result as `fetch_page {"url": "[3]"}`; gatewayd keeps each `[n]`'s address and fetches it. People still get full addresses: citations, the tool call's arguments and the prompt's value show the address (agentd resolves `[n]` from the task's events, gatewayd from its own map). After a restart mid-task an earlier `[n]` isn't resolvable in gatewayd: that fetch is refused, nothing sent.
- **Reader input** (since v0.8.2): the page's title and address go inside the nonce markers; links without a scheme (a two-letter or common TLD, punycode) and IPv4 addresses with a port or path are stripped from the reader's fields too.
- **Quotes by reference** (since v0.8.4). Code splits the item into numbered spans (each line, and each sentence in it; pieces under 24 characters join the next, over 400 are cut at a space; at most about 500 a page) and the prompt shows each after a marker `⟦n⟧` (a page can't write one: those brackets in its text become plain ones). The reader gives a quote as `from` and `to` span numbers (at most 6 consecutive, within one search result), never its text, and code copies the exact words from the source. The schema asks for those members only, with the spans bounded by the item's; a quote with a `text` member, or spans out of range, backwards, too many or across two results, refuses the whole answer. So quotes are exact sentences from the page, chosen by the reader, and the reader can't make up their words. Everything downstream is unchanged: `[quote N]`, the person's exact passages in `tool_result`, the record, the markers, the link stripping.
- **Per-read timeout, 12 s, fail closed** (since v0.8.4). A read that takes longer is skipped like a failed one: the model gets the source's number and that the page reader took too long, nothing from the source; the record's reader entry says `failed` / `timeout`. The run's deadline still applies on top.
- **Cache within a task** (since v0.8.4, `guard/readcache.go`). Keyed by the reader's settings, the question, the address and the full content (SHA-256). The same item read again in the task reuses the checked answer (its quotes get the task's next numbers); on the record as `ok` / `cached` with no tokens. In memory, in the task: never across tasks or people. Only answers that were shown are kept.
- **Injection hardening** (since v0.8.4). When the reader counts an injection, its sentences about it are cut (sentences with inject…, instruct…, claim, false, fake, ignore, link, URL, a port, or an identifier_like_this). Bare IPv4 addresses and names under private or reserved TLDs (`.internal`, `.local`, `.example`, …) are stripped from its fields like other links. Its fields split into sentences at real sentence ends only.
- **When it fails** (an error, a refused answer, or a policy that doesn't allow its model): the source is skipped. The model gets only the address and that it couldn't be read; there is no raw fallback.

### Taint
- A task is **tainted** once its brain has received anything untrusted: web pages, search results, images, and the reader's fields (they come from the same text). The runtime records the taint before the brain sees such a result; every request the brain proposes after that carries `Tainted`. The guard can't follow data through the brain, so taint is per task.
- A task whose input already holds an **earlier assistant turn** is tainted from its start (taint `history`): an earlier answer may carry web-derived text, and the VM can't tell which.
- Taint is on the activity record (each call untrusted or tainted, the run tainted) and in `/tasks/status`. A tainted change or send will need a person's approval once such actions exist.

## 6. Permission prompts
Before data leaves the VM for a task, the person is asked, with exactly what would go out: **Allow once**, **Always allow** (that kind, for the rest of the run) or **Deny**. The model only asks; it can't answer, and it never writes what the person is shown.

- **Kinds.** An action's class is set in the release, never by a model or a policy. Today the class "read, data goes out" is the web connector's three actions, each its own kind: `web.search` (the query goes to a search provider), `web.fetch` (the page's address goes to that site), `web.images` (the query goes to a search provider). Model calls go to the attested model provider and aren't asked about.
- **Settings.** Each run carries the person's setting per kind: `ask` (the default; a kind not named is `ask`), `always` or `never`. A signed policy may cap them with `ask_cap` (per kind: `always`, `ask` or `never`); the narrowest layer wins, so a firm can make its members be asked every time, or turn a kind off. A policy without `ask_cap` caps nothing.
- **The flow.** agentd holds the action (`waiting`, sub-state `permission`; journaled `held`) and adds a `permission` event to the task's stream: the kind, the value that would go out (the masked query or the page's address) and how long it waits. The person's tab answers with `POST /tasks/grant` (`{task, request, kind, decision, value, mac}`, EHBP-encrypted like every task call). agentd checks the grant and hands the action to gatewayd with it; **gatewayd checks it again itself before anything is sent.**
- **The grant.** Until people have identity keys, a grant is `HMAC-SHA256(run secret, "tacy-grant/v1" NUL task NUL request NUL kind NUL decision NUL value)`. The run secret (32 random bytes) is made by the person's tab and sent only inside the run's encrypted body, so only that tab can answer, and the relay can neither read nor forge a grant. A grant for another task, request or kind, a changed value or decision, or a replay is refused (a refused grant leaves the prompt open). A run without a secret can't ask, so kinds on `ask` are refused there (`unavailable`).
- **Edit.** The person may change the value before allowing. The grant carries their value, and gatewayd sends that one (after the same masking and leak scan as any other); the record says it was edited, never the value.
- **Deny.** The action isn't run and the model gets `permission_denied`: answer without it and say it didn't check. The run goes on. **No answer** in time is a deny (`timed_out`; a timeout is never an allow): 10 minutes, but never past the run's deadline less a minute, so the model can still answer.
- **Waiting isn't running time** (since v0.8.1). A chat run's 5-minute limit counts only working time: while a prompt waits and nothing of the run is in flight (no model call, no tool call), agentd stops the run's clock, for the run's running-time budget and the space's day (`safety.Ledger.Pause`), and ends the run when its running time reaches the limit. The run's deadline is an overall cap of 30 minutes after it started, waits included, where the runtime cancels it whatever its running time. So a prompt gets the full 10 minutes, and no run stays open longer than 30 minutes. After an agentd restart, the time a task waited before it counts as running time: a restart can only end a run sooner. (v0.8.0 used the 5-minute running-time limit as the deadline, so a prompt waited about 4 minutes.)
- **Composed addresses** (since v0.8.2). On a tainted task, a page fetch of an address that didn't come from code (not a `[n]`, not a search result's address, not in the person's own messages) is asked about even under Always allow, and its prompt carries `reason`: "This link wasn't in your search results or your message." An Always allow given to another prompt doesn't cover it; only its own answer does. Taint here is the proposing model call's (calls of one step don't taint each other). agentd asks; gatewayd checks it again itself.
- **Hidden characters** (since v0.8.2). A value with control (Cc), invisible format (Cf) or tag-block (U+E0000-E007F) characters is never sent or asked about (denied, record outcome `hidden_characters`), under Always allow too, and a grant carrying one is refused.
- **Task calls** (since v0.8.2). `/tasks/status`, `/tasks/events` and `/tasks/cancel` need a MAC with the run secret (`tacy-task/v1`, op, task) and the user tag; a `/tasks` start needs a run secret. One user tag holds at most 8 of the 64 event streams.
- **Restarts.** A prompt still waiting when agentd restarts is shown again with a fresh timeout; grants given before the restart are gone with it.
- **On the record.** Each call that sends data out says how it was allowed: `allowed_once`, `allowed_always`, `always_setting`, `denied`, `timed_out`, `never` or `unavailable`, and whether the value was edited. Never the value.
- **Rolling back to v0.7.0.** v0.7.0 doesn't ask: it ignores the run secret and the settings and sends what the model proposes. A client that relies on the prompts must refuse v0.7.0 (the chat's minimum release is v0.8.0), so a rollback of the VM goes with a rollback of the client.

## 7. Sub-tasks (later)
`task.spawn` and `task.wait` with depth and width caps and one budget per tree; a child of a tainted task is tainted.

## 8. Slices
Each slice is a release on the usual path (a throwaway VM and the end-to-end test first). v0.7.0 has slices 1 (the task model) and 2 (the reader and taint); v0.8.0 slice 3 (permission prompts). `/run` stays as a shim until the chat moves to `/tasks`, then goes one release later.
